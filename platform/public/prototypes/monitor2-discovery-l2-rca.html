路線A｜已知事故反推監控缺口

① Incident歷史證據

已發生的LP延遲、報價凍結、訂單響應變慢及既有SOP。

② RAG檢索 / Skill執行

RAG僅檢索有來源的事故與SOP；Skill定義固定調查步驟和數據字段需求。

③ 映射內部技術/業務數據

Server ID、LP ID、Symbol、Event Time、Quote Age、Queue Lag、Final Quote Age，使用數據目錄定位表/API。

④ 判斷現有L1/L2覆蓋缺口

⑤ 提交候選指標並回測

⑤ 當前場景的實時參數

可以在「四項規則參數」Tab理解每個計算公式及不同場景爲什麼有不同閾值。

四項參數互相獨立，而且每個L2場景可以各不相同

特別注意：每個L1都有自己的L1報警閾值和Persistence；參與不同L2時，又可以按規則設獨立的參與閾值和Persistence。Correlation Window是L2規則級參數；L2 Severity Score是證據聚合後的動態分數。

配置項計算邏輯 / 條件作用與示例
1. Threshold
數值閾值		xᵢ(t) > θᵢ,L1 → L1獨立候選；xᵢ(t) > θᵢ,L2,r → 參與指定L2規則r同一LP Delay：單點>500ms，L2-A>200ms，L2-B>300ms。互不覆蓋。
2. Persistence
逐L1獨立		持續異常時長 ≥ pᵢ,r；可按連續異常採樣或連續時間定義，需規定缺採樣處理。LP Delay參與L2持續1秒；Final Quote Age持續2秒；Admin Queue持續3秒（均爲模擬）。
3. Correlation Window
L2關聯窗口		T₀ ≤ event_time < T₀+Wᵣ，僅計入同一Correlation Key且符合SEQUENCE的有效信號。本演示12秒；到期未滿足規則即Expired。不另設Grace Period，遲到數據僅記審計。
4. L2 Severity Score
動態聚合分數		Sᵣ(t)=min(100, Σ wᵢ·Iᵢ(t)+b_impact+b_duration)；Iᵢ爲已滿足該規則Threshold及Persistence的指示變量。滿足Mandatory+SEQUENCE+Score≥60 → 提議Risk Ops人工聚合；新增L1刷新得分。權重、分檔均需BU回測校準。
「低/中/高置信度」代表L2規則證據強度等級，不代表客戶風險嚴重度，也不應直接替代 P0–P3事故升級制度；重大Hard Limit單點報警立即送達。

技術落地架構（分離熱路徑與AI）

離線發現

歷史Incident / SOP → RAG檢索 + Skills → 數據Schema註冊與映射 → ML7模型 → 候選L1/L2 → BU驗證/回測/Shadow → Registry。

實時檢測

Admin + Pricing API/Event Stream → Normalization → 持續數值檢測 → L1獨立告警 / L2規則引擎（窗口、AND/OR/SEQ、Score）。

固定上下文

MCP只讀SQL（如Holiday與Session）爲規則提供已批准字段；查詢異常應按Fail-safe策略處理，不調用AI做實時聚合。

Ops審批

新L2 Candidate達標後推薦Risk Ops人工確認；未達標過期留審計；成熟規則未來可審批後自動發車。

異步AI RCA

Incident創建後，AI通過批准的只讀工具查詢DB/日誌、歷史RAG、SOP Skill，生成帶來源及不確定性的報告；Ops確認操作經Incident Service。

POC驗收與風險邊界

必須測試 聚合成功、缺Mandatory、OR替代、錯誤順序、Holiday、不同實體、L1獨立發車。

必須測試 單點L1閾值≠參與L2閾值、各自Persistence、窗口到期、重複關聯、Incident審計。

開發前確認 事件時間同步、跨庫實體ID映射、生產SQL審批/緩存、遲到事件策略、評分校準。

禁止默認自動化 AI執行封禁/改限額/關閉重要事件；未經Risk Ops及BU審批的規則直接推生產。
