**Document ID:** CRMP-PRD-001

This PRD is the product contract for **every screen and feature currently in CRMP Admin**. Operator how-tos live in the [User Guide](/admin/docs/user-guide). Build detail lives in the [TSD](/admin/docs/tsd). Sign-off cases are [UAT-01 … UAT-46](/admin/docs/uat).

## 1. Problem statement

Vantage Markets operates CFD and crypto risk across Monitor 2.0 indicators, desks, and messenger escalation. Today, alarm → root cause → action is fragmented: analysts re-derive context, AI suggestions (if any) lack an independent challenge, and irreversible controls are hard to audit end-to-end.

**We need a centralised risk management plane that:**
- Turns Monitor alarms into explainable AI RCA  
- Challenges high-severity RCA with a second independent AI  
- Lets operators act in messenger (evidence, escalate, dismiss, close, controls)  
- Enforces maker/checker and keeps AI off human-only surfaces  
- Leaves a single spine + audit trail  
- Gives every desk function a named admin page (home, performance, risk log, intel, org, settings, docs)

```mermaid
graph LR
  Mon[Monitor 2.0] --> Crmp[CRMP Admin]
  Crmp --> Lark[Demo Messenger]
  Crmp --> Admin[Vantage admin refs]
  Crmp --> Audit[Spine plus audit]
```

## 5. User journeys (happy path)

### 5.1 High-severity alarm → dual-AI → messenger close
1. Monitor indicator breaches (e.g. COPY concentration).  
2. CRMP creates alert + AI analysis (`SKILL_MATCH` or `RAG_REASONING`) **and** an always-on **how-to-improve** review (data source, dormant indicator health, missing reasoning, new skill pattern, tighten X→Y, response time) with a chatbot to pull data, add facts, challenge, and regenerate.  
3. If severity ≥ `ai.second_opinion_severity` (default BREACH), run `crmp-challenger-v0`.  
4. Risk Analyst opens Demo Messenger thread; **Show evidence**; optionally challenges via chatbot.  
5. Risk Owner reviews primary + challenger; **Close (accept AI)** or escalates / requests control.

```mermaid
graph TD
  Breach[Indicator breach] --> Pack[Alert plus AI pack]
  Pack --> Dual{Severity at BREACH?}
  Dual -->|Yes| Ch[Second AI]
  Dual -->|No| Msg[Messenger]
  Ch --> Msg
  Msg --> Close[Close accept AI]
```


### 5.2 Control with double confirm + checker
1. Operator selects recommended action (e.g. Block user account).  
2. Double-confirm gate → mock Vantage admin ref + link.  
3. If `needs_checker`, Checker approves via Interventions / instructed path.  
4. Audit + Spine record maker/checker outcome.

```mermaid
graph TD
  Act[Recommended action] --> DC{Double confirm?}
  DC -->|No| Stop[Stay in chat]
  DC -->|Yes| Ref[Admin ref]
  Ref --> Ck{Needs checker?}
  Ck -->|Yes| Int[Interventions]
  Ck -->|No| Done[Audited live]
  Int --> Done
```


### 5.3 AI Admin change
1. Maker proposes setting/model/policy in AI Admin.  
2. Distinct Checker approves.  
3. Self-approve is rejected.

```mermaid
sequenceDiagram
  participant Maker
  participant API
  participant Checker
  Maker->>API: propose change
  API-->>Maker: PENDING
  Maker->>API: self-approve
  API-->>Maker: rejected
  Checker->>API: approve
  API-->>Checker: applied
```


### 5.4 Market intel on public snapshot
1. Operator opens Market Intelligence on GitHub Pages.  
2. **Scan now** runs the client demo scan (same templates as live).  
3. Findings, outbox and scan log update locally. No 405.

```mermaid
graph TD
  Scan[Scan now] --> Q{GitHub Pages?}
  Q -->|Yes| Demo[Client demo scan]
  Q -->|No| Live[POST API scan]
  Demo --> Cards[Findings plus outbox]
  Live --> Cards
```


### 5.5 Knowledge tree drill-down
1. Operator opens Knowledge Tree, filter CFD or Crypto if needed.  
2. Clicks a domain (e.g. LP_HEDGE) to fan out skills.  
3. Clicks a skill; inspector fills; **Enter** opens the SKILL.md playbook.

```mermaid
graph TD
  Tree[Knowledge Tree] --> Filter[CFD or Crypto filter]
  Filter --> Dom[Click a domain]
  Dom --> Skill[Click a skill]
  Skill --> Enter[Enter SKILL.md]
```


### 5.6 Unread badge
1. A Monitor 2.0 **Run all indicators** / intel scan / AI simulate creates new work.  
2. Left-nav badge increments (Realtime Alert & Tracker, Messenger, Intel, etc.).  
3. Opening that tab stores “seen” and the badge drops to zero for this browser.

```mermaid
graph LR
  Event[New work] --> Extra[Badge plus extra]
  Extra --> View[Open the tab]
  View --> Seen[Seen equals total]
```

```mermaid
graph LR
  Alarm[Monitor alarm] --> RCA[Primary AI RCA]
  RCA --> Challenge[Second AI]
  Challenge --> Messenger[Demo Messenger]
  Messenger --> Control[Confirmed control]
  Control --> Checker[Checker]
```

### 6.7 Severity formula optimisation + escalation weights (P0–P3) — methods, data, flow

### 6.8 Indicator aggregation linear flow — methods, data, flow

**Methods:** On each single-indicator alert, run skill match and/or RAG retrieval, then check whether the monitor is a member of an aggregate definition (linked timeline / chain). If not, continue the remaining single-indicator path. If yes, continue single RCA in parallel, mark “correlation possible”, and open a wait window for other member monitors. Window expiry with no related alerts → status for RO as single. Related alerts inside the window → aggregate in the Admin UI → RO handles as aggregate. RO may **force-aggregate** while L1 is incomplete (`FORCE_AGGREGATED`, records `missing_l1_at_force`). When L2 is ready, **L2 ops severity = max(fired L1) as floor**, then × pack severity weight (+ multi-L1 nudge) with at most one-band upgrade — never softer than max L1 — and the formula is shown on the board / homepage demo.

| Layer | Detail |
|---|---|
| **Data** | Aggregate defs from `risk_scenario_chains` / `LINKED_SCENARIOS`; sessions in `platform_settings` `indicator.aggregation.sessions` (+ `l1_severities`, `l2_severity`, `l2_severity_calc`, `force_aggregated`, `post_flow`) |
| **Flow** | Alert → skill/RAG → membership → single continue **or** correlated wait → RO single **or** natural / force aggregate → L2 severity calc → post-L2 spine |
| **Surface** | `/admin/indicator-aggregation` · homepage `HomeL1L2AggregationDemo` · `IndicatorAggregationBoard` · `POST /api/indicator-aggregation` (`force_aggregate`, `continue_post_flow`) |

```mermaid
flowchart LR
  A[Single alert] --> B[Skill / RAG lookup]
  B --> C{In aggregate?}
  C -->|No| D[Continue as single]
  D --> E[RO as single]
  C -->|Yes| F[Mark correlation + wait window]
  F -->|Timeout| E
  F -->|Related alerts| G[Aggregate in UI]
  F -->|RO force L1 incomplete| G
  G --> S[L2 severity max L1 x weight]
  S --> H[RO as aggregate]
```

**Acceptance (FR-40):** Linear stepper visible; demo sessions cover no-membership, window-timeout, aggregated, and force-aggregated paths; L2 severity panel shows max(L1) floor + weight; homepage L1→L2 demo; EN + zh-Hant. Operator: User Guide §14B · Build: TSD §11.7 · UAT-48.

## 5. 使用者旅程（快樂路徑）

### 5.1 高嚴重度警報 → 雙 AI → messenger 結案
1. Monitor 指標越線（例如 COPY 集中度）。  
2. CRMP 建立警報＋AI 分析（`SKILL_MATCH` 或 `RAG_REASONING`），並一律產出 **如何改進** 審查（資料源、休眠指標健康、推理缺口、新技能型態、門檻 X→Y、回應時間），可用聊天拉資料、補事實、挑戰、重產。  
3. 若嚴重度 ≥ `ai.second_opinion_severity`（預設 BREACH），跑 `crmp-challenger-v0`。  
4. 風險分析師打開示範 Messenger 執行緒；**顯示證據**；可選以聊天挑戰。  
5. 風險負責人審主 AI＋挑戰者；**結案（接受 AI）** 或升級／要求控制。

```mermaid
graph TD
  Breach[指標越線] --> Pack[警報加 AI 包]
  Pack --> Dual{嚴重度達 BREACH?}
  Dual -->|是| Ch[第二 AI]
  Dual -->|否| Msg[Messenger]
  Ch --> Msg
  Msg --> Close[結案接受 AI]
```


### 5.2 控制：雙重確認＋Checker
1. 操作者選建議動作（例如封鎖使用者帳號）。  
2. 雙重確認關卡 → 模擬 Vantage 管理參照＋連結。  
3. 若 `needs_checker`，Checker 經人工干預／指示路徑核准。  
4. 稽核＋脊柱記錄 Maker／Checker 結果。

```mermaid
graph TD
  Act[建議動作] --> DC{雙重確認?}
  DC -->|否| Stop[留在聊天]
  DC -->|是| Ref[管理參照]
  Ref --> Ck{需要 Checker?}
  Ck -->|是| Int[人工干預]
  Ck -->|否| Done[已稽核上線]
  Int --> Done
```


### 5.3 AI Admin 變更
1. Maker 在 AI Admin 提案設定／模型／政策。  
2. 不同的 Checker 核准。  
3. 自己核准自己被拒絕。

```mermaid
sequenceDiagram
  participant Maker
  participant API
  participant Checker
  Maker->>API: 提案變更
  API-->>Maker: PENDING
  Maker->>API: 自己核准
  API-->>Maker: 拒絕
  Checker->>API: 核准
  API-->>Checker: 已套用
```


### 5.4 公開快照上的市場情報
1. 操作者在 GitHub Pages 打開市場情報。  
2. **立即掃描** 跑用戶端示範掃描（與即時同一批模板）。  
3. 發現、寄件匣、掃描紀錄在本機更新。沒有 405。

```mermaid
graph TD
  Scan[立即掃描] --> Q{GitHub Pages?}
  Q -->|是| Demo[用戶端示範掃描]
  Q -->|否| Live[POST API 掃描]
  Demo --> Cards[發現加寄件匣]
  Live --> Cards
```


### 5.5 知識樹下鑽
1. 打開知識樹，必要時篩 CFD 或 Crypto。  
2. 點領域（例如 LP_HEDGE）展開技能。  
3. 點技能；檢視器填入；**進入** 打開 SKILL.md 劇本。

```mermaid
graph TD
  Tree[知識樹] --> Filter[CFD 或 Crypto 篩選]
  Filter --> Dom[點領域]
  Dom --> Skill[點技能]
  Skill --> Enter[進入 SKILL.md]
```


### 5.6 未讀徽章
1. Monitor 2.0 **執行全部指標**／情報掃描／AI 模擬產生新工作。  
2. 左側徽章增加（即時警報與追蹤、Messenger、情報等）。  
3. 打開該分頁寫入「已看」，本瀏覽器徽章降為零。

```mermaid
graph LR
  Event[新工作] --> Extra[徽章加增量]
  Extra --> View[打開分頁]
  View --> Seen[已看等於總數]
```

```mermaid
graph LR
  Alarm[Monitor 警報] --> RCA[主 AI RCA]
  RCA --> Challenge[第二 AI]
  Challenge --> Messenger[示範 Messenger]
  Messenger --> Control[已確認控制]
  Control --> Checker[Checker]
```

```mermaid
flowchart TD

  B --> C[PENDING_RO 候選]
  C --> D[連線 OpenAI 或 Mock]
  D --> E[分析 → AI 建議卡]
  E --> F{RO 決策}
  F -->|核准驗證| G[僅 BU／UAT — 不部署]
  F -->|要求更多資訊| E
  F -->|駁回| H[關閉]
  G --> I{可選晉升？}
  I -->|制作者≠覆核者| J[SKILL-DISC-*＋M2-DISC-*]
```

**需要的資料**

| 輸入 | 約束 |
|---|---|
| `monitor_indicators` 最新值（CFD／加密代理） | 短特徵窗；不含原始客戶 PII |
| `OPENAI_API_KEY`（可選，伺服器環境變數） | 僅 LIVE 分析；不可進瀏覽器或公開產物 |
| 風險負責人／覆核者工作階段 | 審查變更必要 |
| AI 工程師＋不同 RO | 監控晉升必要（職能分離） |

**方法（七類，與筆記本一致）**

| # | 族類 | 發現 |
|---|---|---|
| 1 | 孤立森林 | 多變量／點異常代理 |
| 2 | CUSUM | 持續體制轉移 |
| 3 | Mahalanobis／聯合距離 | 聯合異常狀態 |
| 4 | LOF | 相對同儕局部離群 |
| 5 | 子群切片 | 產品 × 領域對比 |
| 6 | 序列／領先—滯後 | 前兆型態 |
| 7 | 相關網路 | 跨指標依賴偏移 |

**流程**
1. 執行探索（手動，或 `discovery.auto_on_detectors=true` 時與 `run_detectors` 並行）→ `PENDING_RO`  
2. 連線 OpenAI（環境變數金鑰）或維持 Mock  
3. 分析所選 → 結構化 AI 建議卡  
4. RO：核准進入驗證 · 要求更多資訊 · 駁回 — 絕不自動部署  
5. 可選核准納入監控 → AI 工程師提案／RO 覆核 → `SKILL-DISC-*`＋`M2-DISC-*`  

**驗收（FR-37）：** `/admin/discovery` 與筆記本控制對齊；AI 不可寫審查決策；晉升路徑強制制作者≠覆核者；英＋繁中；筆記本連結可見。操作：使用手冊 §14A · 實作：TSD §11A。

### 6.7 嚴重度公式優化＋升級權重（P0–P3）— 方法、資料、流程

**主迴路（公式）：** 線上加權公式將警報打成 P0–P3。24/7 值班在 Lark AI 事故卡可一鍵**確認 AI 嚴重度準確**（`ai_accurate`，計入每月「維持」），或不準時覆寫 P 並勾選**不准原因代碼**（幅度過重、漏判傳染、單次尖峰…）。AI 每週彙總成新公式（啟停因子、調整權重、微調分帶），開立 `ai_change_requests`；**風險負責人**核准或駁回（Maker ≠ Checker）。卡上另提供 Monitor 2.0 深鏈。

**次迴路（路由）：** 同一批回饋仍匯入 ESC-DEFAULT 的每月**升級維度係數**組合（`escalation.manage` 套用）。

| 層級 | 細節 |
|---|---|
| **方法** | 啟用因子加權和 → 分數 → P 分帶。值班：確認準確 **或** P0–P3＋不准原因代碼（＋選填備註）。每週 AI：增減／啟用因子、權重差、門檻微調 → CR。RO 決定 → 線上公式。 |
| **資料** | `severity.formula.live`；`severity_feedback`（含 `reason_codes_json`、`week_key`）；`ai_change_requests` 實體 `SEVERITY_FORMULA`；每月組合仍用 `escalation_routes.coefficients_json` |
| **流程** | 公式打成 P1 → AI_REPORT（Monitor 2.0 深鏈＋嚴重度回饋）→ 每週建議 → 升級路徑 RO 核准（`sev-formula-loop`）→ AI 績效唯讀鏡像 |

```mermaid
flowchart LR
  Formula[線上嚴重度公式] --> Alert[警報打分如 P1]
  Alert --> Card[AI_REPORT P0-P3＋原因代碼]
  Card --> FB[severity_feedback week_key]
  FB --> Week[每週公式建議]
  Week --> CR[ai_change_requests SEVERITY_FORMULA]
  CR --> RO[風險負責人核准]
  RO --> Live[severity.formula.live]
  FB --> Pack[每月升級係數]
  Pack --> Esc[ESC-DEFAULT 套用]
  Week --> Perf[AI 績效唯讀]
```

**驗收（FR-39）：** `/admin/escalation` 的 `sev-formula-loop` 顯示線上公式＋範例 P＋每週差異＋RO 核准；Messenger `msg-severity-recommend` 有**準確確認**＋原因代碼勾選與 Monitor 2.0 介面連結；每週 CR 為 AI Engineer Maker／RO Checker；AI 績效鏡像每週組合；英＋繁中。操作：使用手冊 §9.2／§9.4／§8.2A · 實作：TSD §11.6 · UAT-45／UAT-47。

### 6.8 指標聚合線型流程 — 方法、資料、流程

**方法：** 每次單一指標告警後，執行技能匹配與／或 RAG 檢索，再檢查該監控是否為某聚合定義（連結時間鏈）的成員。若否，繼續單一指標剩餘流程。若是，並行繼續單一 RCA，標記「可能存在指標關聯」，並開啟等待視窗等其他成員監控。視窗結束且無關聯告警 → 狀態供 RO 按單一處理。視窗內出現關聯告警 → 在管理界面聚合 → RO 按聚合案件處理。L1 未齊時 RO 可**強制聚合**（`FORCE_AGGREGATED`，記錄 `missing_l1_at_force`）。L2 就緒後，**L2 營運嚴重度以 max(已觸發 L1) 為底線**，再 × 嚴重度權重（＋多 L1 推力），最多升一檔且永不低於 max L1；公式在看板／首頁演示可見。

| 層 | 細節 |
|---|---|
| **資料** | 聚合定義來自 `risk_scenario_chains`／`LINKED_SCENARIOS`；工作階段存於 `platform_settings` `indicator.aggregation.sessions`（含 `l1_severities`、`l2_severity`、`l2_severity_calc`、`force_aggregated`、`post_flow`） |
| **流程** | 告警 → Skill／RAG → 成員資格 → 單一繼續 **或** 關聯等待 → RO 單一 **或** 自然／強制聚合 → L2 嚴重度計算 → L2 之後脊柱 |
| **畫面** | `/admin/indicator-aggregation` · 首頁 `HomeL1L2AggregationDemo` · `IndicatorAggregationBoard` · `POST /api/indicator-aggregation`（`force_aggregate`、`continue_post_flow`） |

```mermaid
flowchart LR
  A[單一告警] --> B[Skill／RAG 檢索]
  B --> C{屬聚合？}
  C -->|否| D[按單一繼續]
  D --> E[RO 按單一]
  C -->|是| F[標記關聯＋等待視窗]
  F -->|逾時| E
  F -->|關聯告警| G[界面內聚合]
  F -->|RO 強制 L1 未齊| G
  G --> S[L2 嚴重度 max L1 × 權重]
  S --> H[RO 按聚合]
```

**驗收（FR-40）：** 線型步驟可見；示範工作階段涵蓋無成員、視窗逾時、已聚合、強制聚合；L2 嚴重度面板顯示 max(L1) 底線＋權重；首頁 L1→L2 演示；英＋繁中。操作：使用手冊 §14B · 實作：TSD §11.7 · UAT-48。

## 8. 詳細驗收標準（原型關卡）

1. **技能＋挑戰者：** 模擬 COPY BREACH → `SKILL_MATCH`＋第二 AI 面板，被挑戰時至少 1 項 HIGH 改進。  
1b. **如何改進：** 同一分析（任何嚴重度）開啟如何改進面板（資料源／健康／推理／技能／X→Y／回應時間）與聊天（拉資料／補事實／挑戰／重產／標記滿意）；證據含 IMPROVEMENT 列。  
2. **門檻：** 僅 WARN 的 EQ 模擬在預設 BREACH 門檻下**不**建立挑戰。  
3. **Messenger 路徑：** 顯示證據貼上保險庫；升級前進路徑；排除／結案更新狀態。  
4. **控制：** 封鎖帳號 → 雙重確認 → admin_ref；必要時 Checker 後續。  
5. **AI Admin：** 需要不同 Checker；自己核准被擋。  
5b. **AI 績效：** `/admin/ai-performance` 顯示 KPI（技能匹配、挑戰者、回饋、訓練）且無可寫控制；自 AI 管理可連結。  
5c. **嚴重度 → 權重（FR-39）：** Messenger AI_REPORT 可確認準確或重推薦 P0–P3＋原因代碼，並提供 Monitor 2.0 介面連結；升級路徑顯示每月組合並可套用至 ESC-DEFAULT；AI 績效唯讀鏡像。  
5d. **門檻調整全流程：** Monitor 2.0／管理首頁動態展示取樣 → AI X→Y → CR → 雙重控制 → 套用 → 稽核（AI 不寫線上分帶；編輯器為第 5 步）。  
6. **覆蓋：** UAT 視窗 BREACH／CRITICAL 樣本 100% 已挑戰（允許回填）。  
7. **文件：** PRD／TSD／使用手冊／UAT／生態／路線圖／開放議題／進度英繁皆可渲染；使用手冊對左側每一頁都有操作說明。  
8. **手機：** Messenger 列表→執行緒→返回在約 390px 可用且無整頁溢出。  
9. **Pages：** 登入、messenger 在管理後台開啟、市場情報立即掃描不出現 404／405。  
10. **知識樹：** 領域展開＋進入打開劇本。  
11. **未讀：** 新模擬／掃描／Monitor 全部執行讓徽章增加；打開分頁清除。  
12. **負責人登入：** demo platform owner 角色在 Pages 重新整理後仍在。  
13. **選單真相：** 左側為即時警報與追蹤（非「即時警報」舊名）；無偵測器／AI 分析列表／脊柱日誌列；`/admin/detectors`→Monitor 2.0；`/admin/ai-analyses`→警報；`/admin/spine`→首頁。

正式執行：[UAT 清單](/admin/docs/uat)（UAT-01 … UAT-46）。此包覆蓋每一個管理畫面以及完整 messenger 迴路（收件匣、證據、挑戰、升級、排除、結案、P0–P3 嚴重度重推薦、建議控制、同步）。
